## 2. Common questions & short answers

**Q: Why does SHAP sometimes give a feature a large importance in one direction for one penguin and the opposite direction for another, even though the global ranking says it's important overall?**
A: SHAP values are *local* -- each one explains a single prediction relative to a baseline (the expected model output). A feature can push the prediction up for one individual and down for another (e.g. flipper length matters differently depending on which other features are already "explaining" the species). The global beeswarm plot aggregates the *magnitude* of these local effects, so a feature can rank highly overall while its direction varies case by case. This is expected behaviour, not a bug.

**Q: What exactly does "model-agnostic" mean, and why does it matter?**
A: A model-agnostic method (permutation importance, SHAP's model-agnostic explainers) only needs access to the model's inputs and outputs -- it treats the model as a black box and probes it by perturbing inputs and observing output changes. It doesn't need access to internal weights, gradients, or architecture. That makes it broadly applicable (works on SVMs, random forests, or an API you can only query), but it also means it can be computationally expensive (many re-evaluations) and can be misled by correlated features, since perturbing one feature at a time breaks realistic feature correlations. Contrast this with the adjoint sensitivities in Part 2, which are model-aware: they require differentiating through the model's internals.

**Q: Tree importance and permutation importance gave me different rankings for the same random forest. Which one is "right"?**
A: Neither is unconditionally "right" -- they answer subtly different questions. Impurity-based tree importance measures how much a feature reduced training-set impurity during tree construction; it's biased toward high-cardinality or many-category features and is measured only on the training data, so it can reward pure noise if that noise happens to enable a convenient split. Permutation importance measures how much shuffling a feature degrades held-out predictive performance; it's more trustworthy as a "does this feature actually help the model generalize" signal, and computing it on both train and test sets (as in the flagship boxplot) lets you check for overfitting directly. When they disagree, trust permutation importance for generalization questions, but treat the disagreement itself as informative.

**Q: Does any of this tell us that a feature actually *causes* the outcome?**
A: No. All four Part 1 methods, and the Part 2 adjoint sensitivities, characterize the trained model's behaviour -- not the causal structure of the real world. A feature can rank highly because it's a genuine physical driver, or because it's a proxy/confound correlated with the real driver (the workshop uses Sex in the penguins dataset as a concrete example of this trap). XAI narrows down *where to look* for physical mechanism, and can motivate follow-up domain-driven investigation (as in the landslide and drought-index examples in Dramsch et al. 2025), but it is not a substitute for causal inference or physical reasoning.

**Q: I don't have a data assimilation background -- what does "adjoint" mean here, in plain terms?**
A: Think of it as running the model's sensitivity calculation backward. A normal ("forward") model run takes an initial atmospheric state and produces a forecast. An adjoint (here, computed via reverse-mode automatic differentiation / `torch.autograd.functional.vjp`) asks the reverse question: if I nudge the forecast output by a small amount, how much would I have needed to nudge each point of the initial state to cause that change? The result is a sensitivity map -- everywhere with a large value is a place where the initial conditions strongly influenced that specific forecast output. This is exactly the same mathematical object used in 4D-Var data assimilation to propagate observation-forecast mismatches back to corrections in the initial state; if you've worked with adjoint models or tangent-linear models in NWP, you already have the right mental model for this.

**Q: Why does Part 2 use one fixed perturbation location instead of letting us pick our own?**
A: Two reasons. First, this is an offline-first, pre-committed-artifact demo (by design, so it renders reliably in a 13-minute slot on any machine without GPU access or live model downloads) -- a participant-chosen location would require live inference, which is deliberately gated behind an opt-in `RUN_LIVE` flag rather than being the default path. Second, the fixed example (2m temperature near the Bohai Sea / China coast, 6-hour lead time) is the real worked example from the source ECMWF training material, already validated to show a clean, interpretable sensitivity pattern -- a randomly chosen location and variable might land somewhere numerically noisy or physically uninteresting, which would undercut the teaching point in a short instructor-led segment. If you're running the extended/hands-on version of this material, live inference with participant-chosen locations is exactly the kind of extension worth adding (see `extensions.md`).

**Q: Do I need a GPU to run any of this, either during the workshop or afterward?**
A: Not for the workshop as delivered. Part 1 runs comfortably on Colab's free CPU tier. Part 2 by default only displays pre-rendered images committed to `artifacts/images/` -- no model execution happens. Live AIFS inference is possible afterward if you want to experiment (the underlying checkpoint is a CPU-runnable O48-resolution AIFS model, per the ECMWF training materials), but it's optional, off by default, and not required to get full value from the session.

**Q: This was a 60-minute taster -- where do I go to actually get hands-on and go deeper?**
A: Three pointers: (1) ml.recipes / the `ml-for-science-reproducibility-tutorial` repository by Jesper Dramsch and Valerio Maggio, which this Part 1 notebook is built on and which covers reproducibility practices more broadly; (2) the Dramsch et al. (2025) Nature Geoscience Comment for the conceptual framing and further references; (3) the `extensions.md` pointer shown near the end of this session for what a longer 90-120 minute hands-on version would add to both parts (e.g. participant-chosen locations and live inference in Part 2). Also mention: the session's GitHub repo itself will be public after the placeholder path is confirmed, so participants can revisit the notebooks directly.

**Q: Why do the SHAP and permutation importance rankings sometimes disagree, if they're both supposed to be more trustworthy than tree importance?**
A: They're both more robust than naive impurity importance, but they still measure different things. Permutation importance measures the drop in a chosen performance metric (e.g. accuracy) when a feature is shuffled -- a purely predictive-performance lens. SHAP values are grounded in cooperative game theory (Shapley values) and attribute each prediction's deviation from a baseline fairly across features based on all possible feature coalitions -- a more granular, prediction-level accounting that also captures interaction effects differently. On strongly correlated features especially, the two can rank differently because permutation importance "spreads blame" across correlated features somewhat arbitrarily depending on which one gets shuffled, while SHAP's coalition-based accounting handles that redundancy differently. This is exactly what Exercise 4 asks participants to notice and discuss.

**Q: Is the AIFS example in Part 2 a toy/simplified model, or an actual operational forecasting system?**
A: It's a real, operational-lineage AI weather model from ECMWF (the Artificial Intelligence Forecasting System), run here at a reduced O48 resolution and short 6-hour lead time specifically to keep the demo fast and CPU-runnable for a live teaching setting. The sensitivity methodology (backward/adjoint sensitivities via automatic differentiation) is the same as would be applied at full operational resolution -- only the resolution and lead time are reduced for pedagogical/compute reasons, not the underlying model or method.

## 3. Known failure modes

- **Colab session resets or disconnects mid-session.** Free-tier Colab can disconnect idle or long-running sessions. Recovery is safe and fast: the notebook is fully self-contained (data loads inline via the `palmerpenguins` package with a `seaborn` fallback, models train inline), so a **Runtime > Run all** re-run from a fresh session reproduces the full state in well under the time remaining in most sections. Warn participants proactively at the start of Part 1 that "if your session drops, just Run All again -- nothing is lost, it just takes a minute or two to re-execute."

- **`shap` install/import taking noticeably longer than other packages on first Colab run.** `shap==0.48.0` has native/compiled components and can take longer to import (sometimes 30-60+ seconds on a cold Colab runtime) than numpy/pandas/sklearn. This is most disruptive right before Method 4 if participants haven't pre-warmed it. Mitigation: trigger the `import shap` cell early (e.g. during the Part 1 setup block or even before the framing talk finishes) so it's warm by the time you reach Method 4, and mention out loud that a pause here is expected, not a sign something is broken.

- **Participants without a Google account, unable to open Colab.** Point them to the Binder fallback badge in the README (once published). Binder startup is slower than Colab (container build/pull can take a couple of minutes on a cold cache), so if this comes up, have them start the Binder launch immediately and let it load in the background while following along on-screen in the meantime.

- **numpy/pandas version mismatches or dependency conflicts on participants' personal machines.** If someone tries to run the notebook locally instead of on Colab/Binder during the live session, version drift against the pinned `pyproject.toml`/`uv.lock` dependencies (e.g. numpy>=1.26,<2.0, pandas>=2.2,<2.4) can cause subtle breakage (dtype behaviour changes, deprecated APIs) that's hard to debug live. Strongly steer participants toward Colab or Binder for the duration of the live session; local `uv sync` setup is fine to recommend for later, unhurried exploration, but not as a live-session fallback.

- **`RUN_LIVE` accidentally left on / toggled by a curious participant in Part 2.** Since this is instructor-led and demo-only, this is more of a "don't demonstrate toggling it live unless you've pre-tested that day's environment" note than a participant-facing risk -- but if you take questions by screen-sharing and someone asks you to flip the flag live, be aware it pulls in live inference dependencies/compute that aren't part of the tested offline path, and can eat unplanned minutes or fail outright on unfamiliar hardware.
